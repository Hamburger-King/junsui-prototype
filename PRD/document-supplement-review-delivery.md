## 一、背景与目标

### 1.1 背景

文书办理过程中，律师经常需要用户补充证据、身份信息、合同附件或事实说明。原流程如果依赖聊天或线下传输，容易出现材料要求分散、提交进度不透明、退回原因难追溯、律师遗漏审核以及最终文书交付入口不统一等问题。

### 1.2 产品目标

建立一条可追踪的业务链路：

`律师发起补充要求 → 用户逐项提交 → 律师逐项审核 → 材料齐备 → 文书制作 → 定稿审批 → 用户交付 → 归档完成`

具体目标：

- 用户可以集中查看所有待补充内容、律师要求及参考附件。
- 律师可以跟踪自己发起的补充任务，并及时处理已提交材料。
- 每次提交、退回、豁免、审批和交付均有状态及历史记录。
- 材料齐备后能够自然衔接文书制作与审批，不产生流程断点。
- 最终文书通过统一入口交付用户，并支持后续追溯。

## 二、范围与角色

### 2.1 本期范围

- 文书任务及菜单数字提醒。
- 律师新增补充项及参考附件。
- 用户逐项上传、保存草稿、提交或申请无法提供。
- 律师逐项通过、退回或确认豁免。
- 材料任务状态汇总和文书制作节点生成。
- 文书多版本定稿审批与退回修改。
- 最终文书交付、预览、下载及处理记录。
- 待办分配、通知提醒、权限和审计记录。

### 2.2 用户角色

- **用户**：案件当事人或企业联系人，负责补充材料、查看审核结果和接收最终文书。
- **承办律师**：发起补充要求、审核用户材料、跟踪案件文书进度。
- **文书起草人**：基于已通过材料制作或修改文书，可以是承办律师或协作律师。
- **审批律师**：审核文书定稿，决定通过交付或退回修改。
- **管理员/负责人**：查看团队任务，处理改派、权限和异常任务。

### 2.3 权限原则

- 用户只能访问本人或本企业被授权案件的任务和文件。
- 承办律师可管理自己承办案件的补充要求和审核结果。
- 被指派的审批律师可处理对应文书审批待办。
- 协作人员仅在获得案件权限后访问材料或文书。
- 改派、撤销、删除和最终版本解锁等高风险操作必须记录操作者及时间。

## 三、状态与业务口径

### 3.1 补充项状态

| 状态 | 说明 | 可操作角色 |
|---|---|---|
| 待补充 | 律师已发起，用户尚未提交 | 用户 |
| 草稿 | 用户已上传文件或填写说明但未提交 | 用户 |
| 已退回 | 律师退回，等待用户重新提交 | 用户 |
| 待审核 | 用户已提交材料，等待律师审核 | 律师 |
| 无法提供待确认 | 用户提交无法提供原因，等待律师判断 | 律师 |
| 审核通过 | 律师确认材料符合要求 | 只读 |
| 已豁免 | 律师确认该材料无需继续提供 | 只读 |

状态流转：

- `待补充/已退回 → 草稿 → 待审核 → 审核通过`
- `待审核 → 已退回 → 草稿 → 待审核`
- `待补充/已退回 → 无法提供待确认 → 已豁免`
- `无法提供待确认 → 已退回 → 草稿/无法提供待确认`

### 3.2 文书任务状态

| 状态 | 进入条件 | 退出条件 |
|---|---|---|
| 待补充 | 至少存在一个待用户处理的补充项 | 用户提交全部待处理项 |
| 审核中 | 存在待审核或无法提供待确认项，且无用户待处理项 | 律师完成审核或退回 |
| 待补充（再次） | 任一补充项被退回 | 用户重新提交 |
| 材料齐备 | 所有必填项均为审核通过或已豁免 | 创建文书制作节点 |
| 文书制作中 | 起草人正在制作文书 | 提交定稿审批 |
| 待律师审批 | 文书版本已提交审批 | 审批通过或退回修改 |
| 已交付 | 最终版本审批通过并向用户开放 | 完成归档 |
| 已完成 | 文书已交付且任务归档 | 终态 |

### 3.3 待办和红点数字口径

- USER 菜单红点统计“当前需要用户操作的文书任务数”，不统计补充项数量。
- ADMIN 菜单红点统计“当前账号需要立即处理的待办数”。
- 等待用户补充的任务进入“我发起的”，不计入律师“我的待办”红点。
- 同一文书任务存在多个待审核补充项时，默认聚合为一个律师待办，页面内部展示待审核项数。
- 文书定稿审批单独计为一个待办。

## 四、用户场景与测试

### 用户故事 1：律师发起补充要求（优先级：P1）

作为承办律师，我希望按文书任务逐项创建材料要求并附带示例文件，以便用户准确理解并一次性提交符合要求的材料。

**优先级原因**：这是整个材料补充链路的入口，缺失后续流程无法成立。

**独立测试**：律师创建包含名称、说明、截止时间和参考附件的补充项后，用户侧能够看到一致内容。

**验收场景**：

1. **给定**律师拥有案件权限，**当**新增必填补充项并发送，**那么**用户文书任务出现该补充项且红点数字更新。
2. **给定**律师上传参考附件，**当**发送补充要求，**那么**用户可预览或下载参考附件，且附件不计入用户需提交数量。
3. **给定**补充项尚未被用户提交，**当**律师撤销或修改要求，**那么**用户看到最新要求并收到变更通知。

---

### 用户故事 2：用户逐项补充材料（优先级：P1）

作为用户，我希望按清单逐项上传材料并自动保存草稿，以便在材料较多时分批完成而不丢失进度。

**优先级原因**：直接影响用户完成任务的效率和成功率。

**独立测试**：用户可完成上传、保存草稿、切换补充项和提交，并看到进度变化。

**验收场景**：

1. **给定**任务包含多个补充项，**当**用户切换项目，**那么**当前内容自动保存为草稿。
2. **给定**用户上传至少一个有效文件，**当**提交当前项，**那么**补充项进入待审核并自动定位下一待处理项。
3. **给定**文件格式、大小或安全校验不通过，**当**用户上传，**那么**系统明确提示原因且不生成可提交文件记录。
4. **给定**用户重复点击提交，**当**首次提交正在处理，**那么**系统阻止重复提交。

---

### 用户故事 3：用户申请无法提供（优先级：P1）

作为用户，当客观上无法提供某项材料时，我希望提交原因和替代材料说明，以便律师判断是否允许豁免。

**优先级原因**：避免用户使用空文件或普通备注绕过必填材料，保证审核含义清晰。

**独立测试**：用户不上传文件也可通过专用入口提交原因，律师侧出现“无法提供待确认”。

**验收场景**：

1. **给定**用户选择无法提供，**当**未填写原因直接提交，**那么**系统阻止提交并提示补充原因。
2. **给定**原因填写完整，**当**用户提交，**那么**补充项进入无法提供待确认且计入律师待办。
3. **给定**律师同意豁免，**当**确认操作完成，**那么**用户侧状态变为已豁免且不再要求上传。

---

### 用户故事 4：律师逐项审核材料（优先级：P1）

作为承办律师，我希望不必等待全部材料提交即可逐项审核，以便提前发现问题并缩短文书办理时间。

**优先级原因**：决定材料是否可用于文书制作，是业务质量控制核心。

**独立测试**：律师能够查看用户文件和说明，对每项执行通过、退回或豁免。

**验收场景**：

1. **给定**用户已提交某补充项，**当**律师确认通过，**那么**状态变为审核通过并记录审核人和时间。
2. **给定**材料不完整，**当**律师填写退回原因和新截止时间，**那么**用户侧显示完整反馈并恢复可编辑状态。
3. **给定**用户申请无法提供，**当**律师选择继续要求补充，**那么**必须填写原因并退回用户。
4. **给定**所有必填项均通过或豁免，**当**最后一项审核完成，**那么**任务进入材料齐备并生成文书制作节点。

---

### 用户故事 5：文书定稿审批（优先级：P1）

作为审批律师，我希望查看文书当前版本、历史版本、材料检查结果和修改记录，以便决定通过交付或退回修改。

**优先级原因**：材料齐备后必须通过审批才能形成可交付的最终文书。

**独立测试**：审批律师可完成文书预览、下载、退回和审批通过，版本状态正确更新。

**验收场景**：

1. **给定**起草人提交新版本，**当**审批律师进入待办，**那么**默认展示最新待审批版本和历史修改记录。
2. **给定**文书需要修改，**当**审批律师填写意见并退回，**那么**起草人收到待办，当前版本标记已退回。
3. **给定**文书符合交付标准，**当**审批通过，**那么**该版本锁定为最终版本并生成用户交付记录。
4. **给定**版本已锁定，**当**普通用户尝试覆盖，**那么**系统拒绝覆盖并提示发起新版本。

---

### 用户故事 6：用户接收最终文书（优先级：P1）

作为用户，我希望在文书任务中看到最终文书及处理记录，以便预览、下载和留存。

**优先级原因**：最终交付是业务价值兑现和任务闭环的完成信号。

**独立测试**：审批通过后，用户可从文书任务进入交付页并成功下载最终版本。

**验收场景**：

1. **给定**最终版本审批通过，**当**用户打开文书任务，**那么**状态显示已完成并交付，且提供查看交付入口。
2. **给定**用户点击下载，**当**文件有效，**那么**下载文件名、版本及页面展示一致。
3. **给定**用户发现事实信息错误，**当**查看交付页，**那么**页面说明需联系服务顾问发起新版本，不允许直接修改最终版本。

---

### 用户故事 7：待办、通知与催办（优先级：P2）

作为流程参与者，我希望在需要操作时收到明确提醒，并区分“待我处理”和“等待对方”，以便不遗漏任务。

**优先级原因**：不影响单次功能成立，但直接影响真实业务中的处理及时性。

**独立测试**：不同事件能够生成正确角色的待办和通知，等待对方时不产生错误红点。

**验收场景**：

1. **给定**用户提交材料，**当**提交成功，**那么**承办律师新增待办和站内通知。
2. **给定**律师退回材料，**当**退回成功，**那么**用户红点增加并收到退回原因摘要。
3. **给定**任务临近截止或已逾期，**当**达到提醒时间，**那么**当前责任人收到提醒，律师可主动催办。
4. **给定**律师等待用户补充，**当**查看我的待办，**那么**该任务不计入待处理红点，但可在“我发起的”中跟踪。

---

### 用户故事 8：版本与审计追溯（优先级：P2）

作为管理员或案件负责人，我希望查看完整的材料与文书版本记录，以便处理争议、合规检查和案件复盘。

**优先级原因**：法律业务需要可追溯性，但可在核心操作链路完成后增强。

**独立测试**：任一补充项或文书版本都可查看提交人、文件、时间、审核结论和历史版本。

**验收场景**：

1. **给定**材料被退回，**当**用户重新提交，**那么**上一版文件和退回意见仍可在历史中查看。
2. **给定**人员改派，**当**新律师接手，**那么**历史记录保留原处理人，新操作记录新处理人。
3. **给定**任务已完成，**当**管理员查询，**那么**仍可访问材料、审批和交付记录。

### 边界情况

- 用户只填写普通备注但未上传文件时，不得作为正常材料提交；应引导选择“无法提供材料”。
- 非必填补充项可由律师设置为豁免，但仍需记录原因。
- 已提交或已审核的补充项不得直接删除；需撤销并保留操作记录。
- 律师新增补充项时，如果用户正在编辑其他项目，不得覆盖用户草稿。
- 律师退回时必须填写原因；新截止时间不得早于当前时间。
- 多名律师同时审核同一补充项时，仅首个有效操作成功，其他操作需提示状态已变化。
- 用户或律师失去案件权限后，应立即停止新操作，但保留既有审计记录。
- 文件上传中断时，应展示失败状态并允许重新上传，不得生成空文件记录。
- 任务逾期不自动关闭，仍允许提交；系统需标记逾期并通知承办律师。
- 最终文书交付后如需修改，必须创建新版本，不得覆盖已交付版本。
- 任务被撤销或案件结案时，未完成待办应同步关闭并说明原因。

## 五、功能需求

### 5.1 补充要求发起

- **FR-001**：律师必须能够在有权限的文书任务中新增补充项。
- **FR-002**：补充项必须包含名称、律师说明、是否必填和提交截止时间。
- **FR-003**：律师可以上传零个或多个参考附件，用户可预览或下载。
- **FR-004**：参考附件不得计入用户提交文件数或补充进度。
- **FR-005**：补充项发送后，系统必须更新用户任务及菜单红点。
- **FR-006**：用户提交前，律师可以修改或撤销补充项；修改和撤销必须通知用户并保留记录。

### 5.2 用户材料处理

- **FR-007**：用户必须能够按补充项分别上传多个文件并填写补充说明。
- **FR-008**：系统必须在用户切换补充项时自动保存未提交内容。
- **FR-009**：用户必须能够主动保存草稿。
- **FR-010**：系统必须校验文件类型、单文件大小、上传完整性和安全状态。
- **FR-011**：提交操作成功前必须防止重复提交。
- **FR-012**：用户提交后，补充项必须进入待审核且暂时只读。
- **FR-013**：用户必须能够通过独立入口申请无法提供，并填写原因或替代材料说明。

### 5.3 律师材料审核

- **FR-014**：承办律师必须能够逐项查看用户文件、补充说明及历史版本。
- **FR-015**：律师必须能够将材料标记为审核通过。
- **FR-016**：律师退回材料时必须填写退回原因和重新提交截止时间。
- **FR-017**：退回后系统必须保留上一版文件、用户说明和审核记录。
- **FR-018**：用户申请无法提供时，律师必须选择同意豁免或继续要求补充。
- **FR-019**：所有必填项均审核通过或已豁免时，系统必须将任务标记为材料齐备。
- **FR-020**：材料齐备后系统必须生成文书制作节点，并通知文书起草人。

### 5.4 文书制作与审批

- **FR-021**：文书起草人必须能够提交带版本号的文书供审批。
- **FR-022**：审批页必须展示当前版本、历史版本、修改记录和引用材料检查结果。
- **FR-023**：审批律师必须能够下载或预览当前文书版本。
- **FR-024**：审批律师退回文书时必须填写修改意见，并生成起草人待办。
- **FR-025**：审批通过后系统必须锁定最终版本，记录审批人和审批时间。
- **FR-026**：最终版本锁定后不得被覆盖；修改必须生成新版本。

### 5.5 最终交付

- **FR-027**：审批通过后，系统必须向用户开放最终文书并更新任务状态。
- **FR-028**：用户必须能够预览和下载最终文书。
- **FR-029**：交付页必须展示最终版本号、审批人、交付时间和处理记录。
- **FR-030**：用户发现信息错误时，可以联系服务顾问发起新版本，但不得直接编辑最终文书。

### 5.6 待办、通知和管理

- **FR-031**：系统必须根据当前责任人生成待办，并按统一口径更新菜单红点。
- **FR-032**：律师端必须区分“我的待办”和“我发起的”。
- **FR-033**：用户提交、律师退回、材料通过、文书退回、审批通过和最终交付必须触发对应通知。
- **FR-034**：系统必须支持临期提醒、逾期提醒和律师主动催办。
- **FR-035**：管理员必须能够改派承办律师或审批律师，改派后待办同步转移。
- **FR-036**：所有状态变更、文件操作和人员操作必须记录在处理历史中。

## 六、页面及交互说明

### 6.1 USER 文书任务列表

- 展示任务名称、案件编号、文书类型、当前状态、需要处理的补充项数和截止时间。
- 待用户操作的任务展示“补充材料”。
- 已完成任务展示“查看交付”。
- 菜单红点只统计需要用户操作的任务。

### 6.2 USER 补充材料工作台

- 顶部展示任务信息、总体进度和截止时间。
- 左侧为可滚动补充项清单，支持全部、待处理、待审核和已完成筛选。
- 右侧展示律师说明、参考附件、退回反馈、上传区和补充说明。
- 底部固定保存草稿、无法提供和提交操作。
- 已审核通过或已豁免项目只读。

### 6.3 ADMIN 我的待办

- 展示待我处理、我发起的、处理中和已完成任务。
- 材料审核待办展示已通过/豁免数量及待审核数量。
- 等待用户补充的任务不计入待我处理红点。

### 6.4 ADMIN 材料审核工作台

- 左侧展示全部补充项及状态。
- 右侧展示用户材料、无法提供原因、律师要求和参考附件。
- 待审核项目提供通过和退回操作。
- 无法提供待确认项目提供同意豁免和继续要求补充操作。

### 6.5 ADMIN 文书定稿审批

- 左侧展示版本列表。
- 中间展示文书预览和下载入口。
- 右侧展示审批检查及修改记录。
- 底部固定退回修改和审批交付操作。

### 6.6 USER 最终交付

- 展示交付成功状态、最终文书文件和处理记录。
- 支持预览和下载。
- 明确最终版本已锁定，以及需要修改时的处理方式。

## 七、关键实体

- **文书任务**：关联案件、文书类型、用户、承办律师、当前状态、截止时间、交付信息和处理记录。
- **补充项**：名称、律师说明、是否必填、状态、截止时间、排序、参考附件和审核结论。
- **用户提交版本**：补充项、提交人、文件列表、补充说明、是否无法提供、提交时间和版本号。
- **材料审核记录**：补充项、审核人、审核动作、退回原因、豁免结论和审核时间。
- **文书版本**：文书任务、版本号、文件、起草人、提交时间、审批状态和修改说明。
- **文书审批记录**：文书版本、审批人、审批结论、退回意见和审批时间。
- **交付记录**：最终版本、接收用户、交付时间、下载记录和是否归档。
- **待办**：任务类型、责任人、关联对象、状态、截止时间、完成时间和来源事件。
- **通知**：接收人、通知类型、关联任务、摘要、已读状态和发送时间。

## 八、通知规则

| 事件 | 接收人 | 通知内容 |
|---|---|---|
| 律师新增或修改补充项 | 用户 | 文书名称、补充项数量、截止时间 |
| 用户提交材料或无法提供申请 | 承办律师 | 用户、文书、待审核项名称 |
| 律师退回材料 | 用户 | 补充项、退回原因、新截止时间 |
| 律师通过或豁免材料 | 用户 | 补充项及审核结果 |
| 材料齐备 | 起草人、承办律师 | 可开始文书制作 |
| 文书提交审批 | 审批律师 | 文书名称、版本、截止时间 |
| 文书退回修改 | 起草人 | 修改意见和当前版本 |
| 文书审批通过 | 用户、承办律师 | 最终文书已交付 |
| 临期或逾期 | 当前责任人 | 剩余时间或逾期时长 |

## 九、验收标准

1. 律师新增补充项后，用户侧要求、截止时间和参考附件展示一致。
2. 用户可在不少于 20 个补充项的任务中逐项操作，左侧清单和右侧编辑区独立滚动。
3. 用户切换补充项后重新进入，草稿内容仍存在。
4. 用户正常提交后，律师侧出现待审核状态及正确文件数量。
5. 用户申请无法提供后，律师侧必须出现豁免或继续补充操作，不能直接显示为等待上传。
6. 律师退回后，用户能够看到退回原因、新截止时间和上一版记录。
7. 所有必填项通过或豁免后，任务自动进入材料齐备并生成文书制作节点。
8. 文书审批退回后，起草人可提交新版本，历史版本仍可查看。
9. 文书审批通过后，用户能够预览和下载与审批版本一致的最终文件。
10. USER 和 ADMIN 菜单红点符合本 PRD 定义的任务口径。
11. 未授权用户无法通过直接链接访问案件材料或最终文书。
12. 重复提交、重复审核、并发审批和上传失败均有明确反馈，不产生重复业务记录。

## 十、成功标准

### 可衡量的结果

- **SC-001**：不少于 95% 的补充项能够通过文书任务完成提交，不再依赖线下转发。
- **SC-002**：用户首次进入任务后，可以在 3 分钟内完成单个补充项的上传并提交。
- **SC-003**：100% 的退回操作包含可查看的退回原因、操作人和时间。
- **SC-004**：100% 的最终交付文件能够追溯至唯一审批版本和审批记录。
- **SC-005**：待办红点与实际可操作任务数量一致率达到 100%。
- **SC-006**：用户或律师重复点击提交时，不产生重复任务或重复版本。
- **SC-007**：权限抽查中，未授权材料和文书访问成功次数为 0。

## 十一、数据指标

- 补充任务创建量：统计周期内新创建的文书补充任务数。
- 补充项按时提交率：截止时间前首次提交的补充项数 ÷ 到期补充项总数。
- 一次审核通过率：首次提交即审核通过的补充项数 ÷ 已审核补充项数。
- 平均退回轮次：已完成补充项累计退回次数 ÷ 已完成补充项数。
- 平均材料齐备时长：材料要求首次发送至材料齐备的平均时间。
- 文书审批一次通过率：首次提交审批即通过的文书数 ÷ 已审批文书数。
- 平均交付时长：材料齐备至最终文书交付的平均时间。
- 逾期任务数：统计时点已超过截止时间且责任人仍未完成的任务数。

## 十二、假设

- 一个文书任务在同一时刻只有一名主要承办律师，但可配置协作人员。
- 用户端账号已经与案件及联系人建立授权关系。
- 用户菜单红点按任务统计，页面内部再展示补充项数量。
- 无法提供材料必须经过律师明确豁免，不能由系统自动完成。
- 最终文书审批通过后直接视为交付，不要求用户再次确认收件。
- 实际通知渠道至少包含站内通知；短信、微信等渠道根据现有通知能力接入。
- 文件存储、安全扫描和在线预览能力由现有文件系统提供。

## 十三、超出范围

- 在线共同编辑文书正文。
- 用户对文书逐条在线签署或电子签章。
- 法院、仲裁机构等外部系统的自动提交。
- AI 自动判断证据真实性或直接作出材料通过结论。
- 费用支付、开票和订单退款流程。
- 对历史线下材料进行批量迁移。

## 十四、风险与依赖

- 文件权限或链接过期策略不完整，可能造成敏感材料泄露。
- 状态同步延迟可能导致红点、待办与实际任务不一致。
- 历史文件直接覆盖会造成审核争议，必须采用版本留痕。
- 通知通道失败可能导致用户或律师遗漏截止时间，需要站内待办作为最终兜底。
- 承办律师变更后若待办未同步改派，可能形成无人处理任务。
- 文书最终版本锁定规则需要与现有文件管理和订单交付流程保持一致。
